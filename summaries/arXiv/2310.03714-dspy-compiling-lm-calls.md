# DSPy: Compiling Declarative Language Model Calls into Self-Improving Pipelines — Summary

> [!NOTE]
> **Source:** [2310.03714-dspy-compiling-lm-calls.pdf](../../sources/arXiv/2310.03714-dspy-compiling-lm-calls.pdf) · Khattab, Singhvi, Maheshwari, Zhang, Santhanam, Vardhamanan, Haq, Sharma, Joshi, Moazam, Miller, Zaharia & Potts (Stanford, UC Berkeley, CMU, and others), 2023 · arXiv:2310.03714v1 [cs.CL], 5 Oct 2023 · https://github.com/stanfordnlp/dspy.
> Study-guide summary of the full document. See the original for exact wording and figures.

## Abstract

DSPy is a programming model that replaces hand-written "prompt templates" with declarative, parameterised modules composed into text transformation graphs, plus a compiler ("teleprompters") that automatically optimises any pipeline to maximise a metric — by bootstrapping few-shot demonstrations or finetuning small LMs, rather than by manual prompt engineering. The central argument is that hard-coded prompt strings are brittle and unscalable (conceptually "akin to hand-tuning the weights for a classifier"), and that compiling declarative programs beats hand-crafted prompts while letting much smaller, cheaper LMs stay competitive with proprietary ones.

**Key points**

- **The problem: prompt templates are brittle trial-and-error.** Existing LM pipelines and frameworks (LangChain, LlamaIndex, Semantic Kernel) are implemented with "hard-coded 'prompt templates', i.e. lengthy strings discovered via trial and error." A given string prompt "might not generalize to different pipelines or across different LMs, data domains, or even inputs" — the paper likens hand-tuning prompts to hand-tuning classifier weights.
- **Quantified brittleness (Appendix B/C).** In late September 2023 the LangChain codebase contained **50 strings exceeding 1,000 characters** (generally prompts) versus **none in DSPy**; LangChain had **12 `prompts.py` and 42 `prompt.py` files** dedicated to templating. Example hand-written prompts are huge: PAL math template = **3,982 chars / 566 words**; a text-evidence checker = **4,964 chars / 818 words**; ReAct = **3,889 chars / 593 words**; QA-with-sources = **6,197 chars / 992 words**. DSPy ships "not a single hand-written prompt demonstration for any tasks."
- **The DSPy programming model has three abstractions:** *signatures* (natural-language typed I/O declarations like `question -> answer` that say *what*, not *how*), *modules* (parameterised, composable versions of prompting techniques — `Predict`, `ChainOfThought`, `ProgramOfThought`, `MultiChainComparison`, `ReAct`, `Retrieve`), and *teleprompters* (optimisers that compile a program against a training set and metric).
- **Compiling beats hand-written prompts — quantified gains.** Within minutes of compiling, a few lines of DSPy let GPT-3.5 and llama2-13b-chat self-bootstrap pipelines that outperform standard few-shot prompting "generally by over 25% and 65%, respectively", and outperform pipelines with expert-created demonstrations "by up to 5–46% and 16–40%, respectively." On GSM8K, compiling the right generic modules (rather than string prompts) raises different LMs "from 4–20% accuracy to 49–88% accuracy."
- **End-to-end lifts.** DSPy raises simple programs from **33% → 82%** (GSM8K) and **32% → 46%** (HotPotQA) for GPT-3.5, and **9% → 47%** and **22% → 41%** for llama2-13b-chat, without hand-crafted prompts.
- **Small models made competitive.** A DSPy program compiled to a **770M-parameter T5-Large** scores 39.3% answer EM / 46.0% passage accuracy on HotPotQA using only 200 labelled + 800 unlabelled inputs — "orders of magnitude lower costs for inference than a proprietary LM like GPT-3.5." Compiling can make llama2-13b-chat competitive with GPT-3.5.

**Takeaways**

- Treat prompting as an *optimisation problem*, not a craft: write a declarative program (signatures + modules), supply a metric and a small training set, and let a compiler bootstrap the prompts/finetunes automatically. This is the forward-looking case against artisanal prompt engineering.
- The payoff is measurable and large (double-digit accuracy gains) and it *de-risks model choice* — cheap, small, open models compiled with DSPy rival expensive proprietary ones, and swapping the LM just means recompiling.
- Modularity changes the unit of reuse from a fragile string to a composable, LM-agnostic module, and reframes evaluation from "which LM is best on task X" to "which program P compiled with strategy S is best."

## 1. Introduction

- LMs let researchers build NLP systems at higher abstraction and lower data cost, fuelling an exploding space of **prompting** and lightweight **finetuning** techniques — reasoning elicitation (Chain of Thought, self-consistency), retrieval augmentation, and tool use.
- Interest has grown in **multi-stage pipelines and agents** that decompose complex tasks into manageable LM calls to improve performance.
- **The core problem:** LMs are sensitive to how they are prompted, and this is *exacerbated* in pipelines where multiple LM calls must interact. So the LM calls in existing pipelines and popular frameworks are "generally implemented using hard-coded 'prompt templates', that is, long strings of instructions and demonstrations that are hand crafted through manual trial and error."

> [!IMPORTANT]
> The paper's thesis: this pervasive prompt-template approach is **brittle and unscalable** — "conceptually akin to hand-tuning the weights for a classifier." A given string prompt may not generalise across pipelines, LMs, data domains, or even inputs. DSPy pushes pipeline building *away from manipulating free-form strings and closer to programming*, where a compiler automatically generates optimised LM invocation strategies and prompts from a program.

- **The neural-network analogy.** DSPy draws on the consensus behind neural-net abstractions: (1) general-purpose layers compose into any architecture, and (2) weights are trained by *optimisers* instead of hand-tuned. DSPy applies the same to LM pipelines.
- **The three contributions:**
  1. Translate string-based prompting techniques (including Chain of Thought and ReAct) into **declarative modules** carrying natural-language typed **signatures** — task-adaptive components akin to NN layers.
  2. **Parameterise** each module so it can learn its behaviour by iteratively bootstrapping useful demonstrations within the pipeline; pipelines are define-by-run computational graphs (PyTorch-inspired).
  3. A **compiler** (Sec 4) that optimises any DSPy program to improve quality or cost, driven by **teleprompters** (general-purpose optimisation strategies).
- **Headline results (quantified):** without hand-crafted prompts and within minutes to tens of minutes of compiling, DSPy raises simple programs from **33% → 82%** (Sec 6, GSM8K) and **32% → 46%** (Sec 7, HotPotQA) for GPT-3.5, and from **9% → 47%** and **22% → 41%** for llama2-13b-chat. Programs compiled to small open LMs (770M T5, llama2-13b-chat) are competitive with expert-written prompt chains for proprietary GPT-3.5.

> [!NOTE]
> DSPy is pronounced "dee-ess-pie"; it is the second iteration of the earlier Demonstrate–Search–Predict (DSP) framework. **Teleprompters** are named from abstracting/automating the task of prompting "at a distance, without manual intervention."

## 2. Related Work

- **Inspiration from deep-learning frameworks.** Torch, Theano, Chainer, and PyTorch provided powerful abstractions; DSPy seeks the analogous conceptual framework for what it calls **foundation model programming** — differentiable programming applied to LM calls rather than neural networks, borrowing PyTorch syntax.
- **In-context learning** is the key mechanism; instruction tuning lets prompting elicit sophisticated behaviour, and weak supervision that once needed hand-built heuristics is now done by LMs.
- **Toolkits.** LangChain, Semantic Kernel, LlamaIndex and other retrieval/agent libraries provide pre-packaged chains and agents — but "they suffer from the pervasive prompt engineering challenges we address in DSPy: they express task-specific behavior through hand-written prompt templates" (see Appendix B).
- **Prompt optimisation research.** Others apply discrete optimisation and RL to find effective prompts, but generally for a *single* logical LM call. DSPy generalises this: it optimises *arbitrary pipelines* from high-level declarative signatures by bootstrapping multi-stage demonstrations with constraints, and its teleprompters can in principle use cross-validation, RL/LM feedback, or Bayesian hyperparameter optimisation.

## 3. The DSPy Programming Model

DSPy treats LMs as abstract text-generation devices and optimises their use in arbitrary computational graphs. Programs are Python: input → series of steps → output. Three abstractions: **signatures**, **modules**, **teleprompters**.

### 3.1 Natural language signatures can abstract prompting & finetuning

- A **signature** is a natural-language typed declaration of a function — a short declarative spec of *what* a text transformation must do (e.g. "consume questions and return answers"), not *how* to prompt for it. Formally: a tuple of input fields and output fields (plus an optional instruction); field roles are inferred from field names.
- **Two benefits over prompts:** (1) they compile into self-improving, pipeline-adaptive prompts *or finetunes* (via bootstrapping demonstrations), and (2) they handle structured formatting/parsing, reducing brittle string manipulation.
- **Shorthand:** `dspy.Predict("question -> answer")` is a complete QA system. Field names expand into instructions, so `english document -> french translation` prompts for translation.

### 3.2 Parameterized & templated modules can abstract prompting techniques

- To use a signature you declare a **module** with it; the module is a callable (like a PyTorch layer) that formats the prompt with demonstrations, calls the LM, and parses the outputs. In compile mode it also tracks input/output **traces** to help the teleprompter bootstrap demonstrations.
- **`Predict`** is the core module. Built-in higher modules — **`ChainOfThought`, `ProgramOfThought`, `MultiChainComparison`, `ReAct`** — generalise techniques from the literature (Wei et al. 2022; Chen et al. 2022; Yoran et al. 2023; Yao et al. 2022) and are interchangeable for any signature. E.g. swapping `Predict` → `ChainOfThought` makes the system think step by step. `ChainOfThought` is implemented in a few lines: it prepends a `rationale` output field ("Reasoning: Let's think step by step.") and calls `Predict`.

> [!TIP]
> The paper explicitly contrasts DSPy's few-line `ChainOfThought` against Appendix C, which reproduces the "long reasoning prompts hand-written by sources ranging from recent research to popular prompting libraries." The module captures the *technique*; the compiler supplies the *content*.

- **Parameterization.** Any LM call implementing a signature must specify: (1) the LM, (2) the instructions and per-field string prefixes, and — **most importantly** — (3) the **demonstrations** (few-shot examples for frozen LMs, or training data for finetuning). DSPy focuses on automatically generating and selecting useful demonstrations.
- **Tools.** `dspy.Retrieve` supports ColBERTv2, Pyserini, Pinecone; experimental `dspy.SQL` and `dspy.PythonInterpreter` (sandboxed).
- **Programs** compose modules in a **define-by-run** interface: declare modules in `__init__`, connect them with arbitrary control flow in `forward`. A complete RAG system is ~6 lines (`Retrieve` + `ChainOfThought("context, question -> answer")`).

### 3.3 Teleprompters can automate prompting for arbitrary pipelines

- A **teleprompter** is an optimiser: it takes a program + training set + metric and returns a new optimised program.
- **Label-efficiency is central.** Training sets may be tiny (a handful of examples) and *incomplete* (only inputs needed); typically labels are assumed only for the program's final output, not intermediate steps. Building a new pipeline just means **recompiling**, not annotating pipeline-specific data.
- **Metrics** can be simple (exact match, F1) or entire DSPy programs (e.g. one that checks faithful grounding of answers). Example: compile RAG with `BootstrapFewShot(metric=answer_exact_match)` — the teleprompter simulates RAG on the example(s) and collects per-module demonstrations that lead to valid output.
- **Composition via teacher programs.** A teleprompter can sample demonstrations from a *teacher* program, enabling expensive programs (large-LM ensembles) to supervise cheap ones. Example: `BootstrapFinetune` with `teacher=compiled_rag` finetunes Flan-T5-large from an unlabelled question set, filtering ungrounded answers with `answer_passage_match`.

## 4. The DSPy Compiler

Compiling = automatically optimising any program via a teleprompter, which improves quality (or cost) through prompting **or** finetuning (unified in DSPy). Typical teleprompters have three stages.

| Stage | Name | What it does |
|---|---|---|
| **1** | Candidate Generation | Recursively finds all unique `Predict` modules (predictors); for each, generates candidate parameter values — instructions, field descriptions, and (the focus) **demonstrations**. `BootstrapFewShot` simulates a teacher (or the zero-shot program) on training inputs, tracks multi-stage traces thread-safely, and keeps traces that pass the metric as candidate demonstrations (rejection-sampling-like). |
| **2** | Parameter Optimization | Selects among candidate demonstrations/instructions with hyperparameter search — random search or Tree-structured Parzen Estimators (HyperOpt, Optuna). Variants: `BootstrapFewShotWithRandomSearch`, `BootstrapFewShotWithOptuna`. `BootstrapFinetune` instead uses the demonstrations to update LM weights, optimising average quality via cross-validation. |
| **3** | Higher-Order Program Optimization | Modifies the program's control flow. Simplest form: **ensembles** — bootstrap multiple program copies and reduce their predictions (e.g. majority vote). Future work: dynamic test-time bootstrapping and automatic backtracking. |

> [!NOTE]
> LMs are unreliable individually but "rather efficient at searching the space of solutions for multi-stage designs." A well-decomposed program can usually find a few training examples where the LM passes signature+metric constraints, enabling iterative bootstrapping.

## 5. Goals of Evaluation

The paper focuses on the most pressing issue: **the role of hand-written, task-specific prompts** in achieving performant systems. Three hypotheses:

- **H1** — DSPy can replace hand-crafted prompt strings with concise, well-defined modules *without reducing quality or expressive power*.
- **H2** — Parameterizing modules and treating prompting as optimisation makes DSPy better at *adapting to different LMs*, and it may *outperform expert-written prompts*.
- **H3** — The resulting modularity makes it possible to *more thoroughly explore* complex pipelines with useful characteristics or nuanced metrics.

> [!TIP]
> A goal is to shift evaluation from underspecified questions like "how do different LMs compare on GSM8K" toward "how they compare on GSM8K with program P compiled with strategy S" — a well-defined, reproducible run. The broader aim: "reduce the role of artful prompt construction in modern AI in favor of the development of new modular, composable programs and optimizers."

## 6. Case Study: Math Word Problems (GSM8K)

- **Setup.** GSM8K grade-school math; 200 train + 300 dev sampled from the official train set; final evaluation on the 1.3k official test set; accuracy = final numerical value in the LM output.
- **Programs** (all generic, none math- or LM-specific): `vanilla` = one-step `Predict`; `CoT` = `ChainOfThought`; `reflection` = `ThoughtReflection` (samples **5** reasoning chains, then a built-in `MultiChainComparison` compares them in parallel to produce a new answer, generalising Yoran et al. 2023).
- **Compilers.** `none` (zero-shot); `LabeledFewShot(k=8)`; `BootstrapFewShotWithRandomSearch` (`bootstrap`); nested `bootstrap×2` (bootstrap using the bootstrapped program as teacher); `Ensemble` of the top-7 candidate programs with majority voting. `+human CoT` uses GSM8K's human reasoning chains.
- **Cost.** Compiling runs on the order of minutes to tens of minutes — even expensive settings need only a few thousand program runs (≈10–20 trials over 150–300 validation examples), and they parallelise.

**Findings.**
- `vanilla` (direct answer, no reasoning) struggles — worst under `none` and `fewshot` — but improves substantially with `bootstrap` and `bootstrap×2`; bootstrapped prompts let the LM reason in the answer field first.

- `reflection` is the clear winner though only a few lines longer; `CoT`+ensemble is also strong.
- **External comparisons** (informal): Zhang et al. 2022 report 48% (text-davinci-002), 59.4% (manual CoT + codex), 62.8% (auto CoT); Wang et al. 2022b report 57% CoT for PaLM-540B → 74% with self-consistency; Llama2 authors report 28.7% (13b), 42.2% (34b), 56.8% (70b) — DSPy's 13b program is competitive with their **34b** result despite using no human reasoning chains. GPT-4 report: GPT-3.5 = 57.1%, GPT-4 = 92% (but GPT-4 was pretrained on a GSM8K train subset).

## 7. Case Study: Complex Question Answering (HotPotQA)

- **Setup.** Multi-hop QA on HotPotQA open-domain "fullwiki"; ColBERTv2 retriever over the Wikipedia 2017 abstracts dump. Test set is hidden, so the official validation set (1,000 sampled "hard" examples) is used for testing; train set split 70/30, keeping only "hard" examples; 200 train + 300 dev. Metrics: answer exact match (Ans/EM) and pair-retrieval accuracy (Psg).
- **Programs.** `vanilla` (`question -> answer`); baseline `RAG` (`ChainOfThought` over retrieved context — does not excel); `ReAct` (built-in agent, `tools=[Retrieve(k=1)]`, `max_iters=5`); `BasicMultiHop` (custom, 2 hops: generate a `search_query`, retrieve, repeat, then answer — simulates Baleen/IRRR, similar to IRCoT).
- **Compilers.** Same as GSM8K, plus compositions: `ReAct` bootstrapped from an earlier bootstrap; `multihop` finetuned to **T5-Large** via `BootstrapFinetune`.

**Findings.**
- `CoT RAG` self-bootstraps to raise answer EM but is limited by retrieval recall (queries only from the original question). The `react` and `multihop` programs generate queries over multiple hops.
- **`multihop` is best overall**; `bootstrap` again strongly beats `fewshot`, and `bootstrap` / `bootstrap×2` outperform both few-shot prompting (multihop) and expert human reasoning (react).
- **Small-LM parity:** compiling makes llama2-13b-chat competitive with GPT-3.5.
- **T5-Large finetune:** `multihop_t5` (770M params) scores **39.3% answer EM / 46.0% passage accuracy** on dev using only **200 labelled + 800 unlabelled** inputs, with a teacher = ensemble of two llama2-13b-chat multihop programs — "orders of magnitude lower costs for inference than a proprietary LM like GPT-3.5."
- **External comparisons** (with caveats about methodology variation): Si et al. 2022 = 25.2% EM (CoT); Sun et al. 2022 = 26.5% (recite-and-answer, PaLM-62B); Wang et al. 2022a = 33.8% EM / 44.6% F1 (self-consistency, PaLM-540B); Yao et al. 2022 = 27.4% EM (ReAct, PaLM-540B), 30.8 (text-davinci-002), 35.1% with an added CoT+self-consistency step; Trivedi et al. 2022 = 49% (code-davinci-002 pipeline, 500-question sample).

## 8. Conclusion

- DSPy is "a new programming model for designing AI systems using pipelines of pretrained LMs and other tools," built on three concepts — **signatures, modules, teleprompters**.
- Two case studies show rapid development of highly effective systems using relatively small LMs. The framework has been open-source for close to a year and has compiled many programs across tasks from information extraction to low-resource synthetic data generation (left to future work under controlled conditions).

> [!IMPORTANT]
> The forward-looking claim: while in-context learning has been transformative, "the true expressive power in this emerging paradigm is in building sophisticated text transformation graphs in which composable modules and optimizers (teleprompters) come together to leverage LMs in more systematic and reliable ways" — i.e. compiled, declarative pipelines over artisanal prompt strings.

### Appendix A — Advanced Signatures
Signatures can be Python classes for explicit control: a docstring instruction plus `dspy.InputField`/`dspy.OutputField` with descriptions and optional types (`bool`, `int`, `float`, `list`, `dict`; default = free-form string). Example: `GenerateSearchQuery` produces IR queries mediated by an LM-generated question.

### Appendix B — Comparison with LangChain and LlamaIndex (the quantified critique)
- LangChain/LlamaIndex target *application developers* wanting pre-packaged components/chains; DSPy targets the *fundamental prompt-engineering problem* with composable operators (signatures, modules, teleprompters) and automatic compilation.
- **Informal study (late Sept 2023):** LangChain codebase had **50 strings > 1,000 characters** (generally prompts) vs **0 in DSPy**; **12 `prompts.py` + 42 `prompt.py`** files dedicated to templating. DSPy "does not contain a single hand-written prompt demonstration for any tasks."
- LangChain's PAL chain uses a **3,982-character** template with 8 math problems; its per-database SQL prompts average **1,058 chars**; QA-with-sources and Graph QA templates average **1,337** and **722 chars**. The argument: LM- and task-adaptive prompts bootstrapped automatically are "far more power[ful] (and are far more modular) than hard-coding a prompt per database provider."
