# From Agent Traces to Trust: A Survey of Evidence Tracing and Execution Provenance in LLM Agents

> [!NOTE]
> Source: [2606.04990-agent-execution-provenance.pdf](../../sources/arXiv/2606.04990-agent-execution-provenance.pdf) — Yiqi Wang, Jiaqi Zhang, Zhangkai Wu, Taotao Cai, Zirui Liu, Qingqiang Sun, Zequn Sun, Manqing Dong, Mingkai Zheng, Xuefei Yin, Yanming Zhu (Griffith University and others), *From Agent Traces to Trust: A Survey of Evidence Tracing and Execution Provenance in LLM Agents*, arXiv preprint 2606.04990v4 [cs.CR], 28 June 2026. https://arxiv.org/abs/2606.04990
> This is a non-peer-reviewed arXiv preprint survey — treat its framing and taxonomy as the authors' proposed synthesis, not settled consensus.

## Abstract

This survey argues that as LLM agents move from passive text generators to autonomous systems that plan, call tools, retrieve, access memory, act on environments, and collaborate with other agents, their behaviour becomes hard to verify, debug, and audit — because agents are judged almost entirely on their final answers, and "a correct answer reveals nothing about how an output was produced, what evidence supported each claim, whether tool calls were justified, how memory shaped later decisions, or where execution failures originated." The authors' central move is to look past the output to the execution process itself and structure it as **execution provenance**: "the full typed graph of an agent execution", with **evidence tracing** as its projection onto evidence-support relations. This provenance layer is offered as a single, process-level accountability framework unifying otherwise-separate concerns — retrieval grounding, tool-use safety, memory, observability, debugging, audit, and recovery. The single most citable claim: final-answer accuracy "evaluates only the endpoint of an execution; it does not explain how an output was produced." The survey contributes a six-dimensional taxonomy, a review of seven research threads, and a mapping of benchmarks/metrics to provenance capabilities.

## The core idea: process-level accountability, not endpoint accuracy

The survey names a "process-level accountability gap" in agent systems: evaluation stops at the final answer, but the answer does not say which evidence backed each claim, whether tool calls were justified, whether memory items were relevant and trustworthy, or which step caused a failure. Reconstructing what an agent *did* therefore requires treating the execution as a structured, typed record rather than a flat chronological transcript.

Two defined terms anchor the framework (verbatim definitions from the paper):

- **Execution provenance** — "the complete typed representation of an agent run, including evidence units, execution units such as retrieved documents, tool calls, parameters, observations, memory accesses, intermediate claims, actions, inter-agent messages, and final outputs, and their causal, procedural, dependency, update, contradiction, and invalidation relations." It is the *process view*.
- **Evidence tracing** — "the projection of this provenance structure onto evidence-support and influence relations between evidence units and agent claims, decisions, or actions." It is a *sub-problem* of execution provenance (every evidence-support link is in the provenance graph) — the *support view*.

The distinction the survey stresses: **traceability** makes recorded artifacts inspectable; **provenance** goes further by modelling the *typed relations* among them. A structured log answers "what happened"; an execution graph answers "what depended on what"; claim-support links make grounding and accountability *measurable*. The framework is explicitly informed by prior provenance/observability traditions — W3C PROV-DM (entities, activities, agents; relations of use, generation, derivation, revision, invalidation), OpenTelemetry (traces and spans), and agent-observability systems like AgentOps and AgentTrace — specialised to the semantic and procedural objects LLM agents add (retrieved passages, generated claims, tool-call rationales, memory items, NL observations, external state changes, inter-agent messages).

## The six-dimensional taxonomy (Section 2, Table 1)

The survey organises provenance-aware agent work along six dimensions:

1. **Trace sources** — the components/execution boundaries that generate provenance-relevant artifacts: reasoning, retrieval, tool use, MCP server/host boundaries, memory, environment, and multi-agent communication. (Representative work: ReAct, Reflexion, ToolLLM, WebArena, AutoGen, AgentTrace, MCP-SafetyBench.)
2. **Evidence and execution units** — two kinds of recordable unit. *Evidence units* are semantic objects that support/contradict/invalidate/contextualise claims (documents, passages, observations, tool outputs, memory items, policies, intermediate claims, final answers). *Execution units* are procedural objects recording what the agent did (reasoning steps, retrieval calls, tool invocations, parameters, tool manifests, permission scopes, memory operations, actions, inter-agent messages). The distinction is not absolute — a tool output is both an execution result and possible evidence for a later claim.
3. **Provenance relations** — the typed links that turn raw units into provenance. PROV-compatible base relations USE, GENERATE, DERIVE, plus agent-specific relations SUPPORT, DEPEND-ON, CONTRADICT, INVALIDATE, TRIGGER, UPDATE. (Example: a passage may SUPPORT a claim; a tool call may DEPEND-ON generated parameters; a new observation may INVALIDATE a plan; a failed action may TRIGGER recovery.)
4. **Tracing granularity and timing** — *Granularity*: run-level (coarse audit), step-level (debugging), tool-call/parameter-level (safety enforcement), claim-level (factual attribution), token/span-level (finest, most expensive). *Timing*: pre-execution (block unauthorised actions), runtime (policy enforcement, information-flow control), post-hoc (audit and diagnosis), continuous (persistent memory, long-horizon workflows). Choice depends on risk: low-risk RAG may need only claim-level post-hoc attribution, whereas high-impact tool use may need runtime parameter-level provenance.
5. **Representation forms** — structured logs, execution graphs, evidence graphs, claim-support graphs, provenance graphs, runtime state. Determines how traces are encoded for inspection, comparison, enforcement, or evaluation.
6. **Trust functions** — the downstream *purpose* of tracing (the reason to record, not just "more logs"): **verification** (are claims/actions supported by evidence?), **attribution** (which evidence/tool output/memory item/message contributed?), **debugging** (localise failures), **safety enforcement** (prevent untrusted/unauthorised influence reaching sensitive actions), **audit** (reconstruct executions for review and accountability), **failure attribution**, and **recovery** (retry, compensate, roll back, or repair).

### Four design tensions (Section 2.2)

The taxonomy surfaces four tensions that recur through the survey: (1) chronological logging ≠ semantic provenance — a log records what happened but may not show whether evidence supported a claim; (2) component-level tracing does not guarantee end-to-end accountability, because failures propagate across retrieval, tools, memory, environment, and other agents; (3) static schemas standardise objects/relations, but runtime safety needs online source tracking, policy checking, and dependency-aware enforcement; (4) trace completeness must be balanced against deployability — fine-grained provenance improves verification/debugging/audit/recovery but raises storage cost, privacy exposure, annotation burden, and complexity.

## The seven research threads

The survey reviews existing methods across seven threads: (1) **provenance representation** (structured logs → execution graphs → evidence/claim-support graphs → provenance graphs and runtime state); (2) **evidence attribution** (citation-, atomic-fact-, and source-checking evaluation — e.g. ALCE, FActScore, RAGChecker, SourceCheckup — asking whether a cited source actually supports the claim); (3) **tool-use provenance** (Section 4); (4) **runtime guardrails**; (5) **provenance-bearing memory** (Section 5); (6) **observability**; and (7) **failure diagnosis** (TRAIL localises failures to steps/components; AgenTracer uses counterfactual replay and fault injection to attribute failures to responsible agents/steps; Aegis uses positive–negative trajectory pairs to identify faulty agents and error modes).

Three representation forms and their roles (Table 2): *structured logs* → execution observability and reconstruction; *execution graphs* → influence analysis for debugging, audit, and recovery; *evidence/claim-support graphs* → measurable grounding and accountability.

## Open problems (Section 7) and conclusion (Section 8)

The authors judge the field to have made progress but to remain **fragmented**: systems increasingly record execution artifacts, "but they rarely explain how evidence, tools, memory, observations, messages, and actions jointly shape an agent's final answer or external behavior." Six open challenges:

- **Unified/interoperable trace schemas** — no schema jointly represents reasoning, retrieval, tool calls/outputs, memory reads/writes, inter-agent messages, intermediate claims, final responses, and external state changes; future schemas should connect operational trace structures (PROV-DM, OpenTelemetry, OpenLineage, PROV-AGENT) with semantic evidence relations.
- **Claim-level and semantic provenance** — outputs contain multiple claims of differing support; string-level citation matching is insufficient when evidence is paraphrased, summarised, compressed into memory, passed through tools, or reused by another agent. Semantic provenance across transformations remains open.
- **Memory and multi-agent provenance** — memory items should carry provenance metadata (source, write time, update history, retrieval context, downstream usage, conflict status, invalidation); a memory item from user input vs. retrieved evidence vs. a tool output should carry different trust implications. Memory-poisoning/injection attacks can influence future behaviour without modifying weights. Multi-agent settings add a responsibility-attribution problem.
- **Runtime safety, enforcement, and recovery** — guardrails inspecting only the final answer or current tool call miss source-to-sink dependencies; provenance-aware guardrails should reason over the evidence/memory/observations/external content that influenced a proposed action. The under-addressed piece is *recovery*: using provenance to invalidate stale memory, quarantine contaminated evidence, retry with corrected parameters, request human approval, roll back state, or replay from safe checkpoints.
- **Realistic benchmarks** — no benchmark family fully evaluates provenance across retrieval, tools, memory, multi-agent communication, safety attacks, and recovery; evaluation should move from answer-/task-/attack-level toward *trace-level*.
- **Privacy-aware audit infrastructure** — provenance traces may contain sensitive user data, credentials, API arguments, and internal reasoning; without trace minimisation, access control, anonymisation, retention, encryption, and selective disclosure, the provenance layer itself becomes a compliance/security risk.

The conclusion restates the thesis: the shift to tool-using, memory-updating, multi-agent systems makes final-answer correctness "insufficient for trustworthiness"; reliable systems "must also expose where answers come from, which evidence supports them, how tools and intermediate actions contribute to them, and where failures or unsafe influences enter the execution process." The authors call for evidence tracing and execution provenance to become "a first-class infrastructure layer for reliable agent systems" — traceable, auditable, and recoverable.
