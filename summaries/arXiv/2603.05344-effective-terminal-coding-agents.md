# Building Effective AI Coding Agents for the Terminal: Scaffolding, Harness, Context Engineering, and Lessons Learned

> Source: arXiv:2603.05344 (submitted 13 March 2026, v3). Bui (Nghi D. Q. Bui). PDF in `../../sources/arXiv/2603.05344-effective-terminal-coding-agents.pdf`.

## Thesis
The paper presents OPENDEV, an open-source, terminal-native, interactive coding agent written in Rust, and documents (rather than benchmarks) the design decisions, trade-offs, and lessons from building a production-ready CLI agent. Its central claim is that effective long-running terminal agents are engineered as a compound AI system: workload-specialized per-workflow model routing, a scaffolding/harness split, schema-level (not runtime) safety, and context engineering treated as a first-class concern. It is positioned as the first comprehensive technical report for an open-source terminal-native interactive coding agent, filling the gap left by closed systems (Claude Code) and benchmark-oriented frameworks (SWE-Agent).

## Key findings
- **Scaffolding vs. harness split (§2.2, §3.2 lesson).** Scaffolding assembles the agent once before the first prompt (system prompt compiled, tool schemas built, subagents registered); the harness handles all runtime orchestration (tool dispatch, compaction, safety, persistence). Eager construction (build prompt + schemas in `__init__`) eliminates first-call latency and MCP-discovery race conditions. A single parameterized `MainAgent` class replaced an earlier agent-type class hierarchy that created a diamond problem.
- **Safety via schema gating, not runtime checks (§2.2, §3.3 lesson).** Five-layer defense in depth: prompt guardrails, schema-level tool gating (dual-agent separation), runtime approval with persistent permissions, tool-level validation (`DANGEROUS_PATTERNS` blocklist, stale-read detection), and lifecycle hooks. Making unsafe tools invisible (absent from the schema) is more robust than permission checks — a Planner subagent given only read-only tools cannot attempt writes because write tools do not exist in its schema. This replaced a brittle four-tool plan-mode state machine that would get stuck in read-only state.
- **Adaptive Context Compaction — five graduated stages (§2.3.6, Alg. 1).** Thresholds: warning (70%), observation masking (80%), fast pruning (85%), aggressive masking (90%), full LLM compaction (99%). Cheaper masking/pruning stages usually reclaim enough space to avoid expensive LLM summarization. **ACC reduces peak context consumption of observations by ~54%**, often eliminating emergency compaction over typical 30-turn sessions. Tool outputs consume **70–80% of context** in a typical session.
- **Tool-result optimization and offloading (§2.3.2).** Per-tool-type summarizers compress raw outputs to 50–200 char summaries (e.g., "Read file (142 lines, 4,831 chars)"); outputs over 8,000 chars are offloaded to scratch files with a 500-char preview + reference path. This extended typical session length from **15–20 turns (before overflow) to 30–40 turns without compaction**; a single test suite could otherwise consume 30,000 tokens.
- **Provider prompt caching + conditional composition (§2.3.1).** The system prompt is factored into priority-ordered markdown sections loaded by predicate (filter→sort→load→join). Splitting into stable (cacheable) + dynamic parts and marking the stable prefix `cache_control: ephemeral`; the stable portion is 80–90% of the prompt, yielding **~88% reduction in input token cost for the cached portion**. Typically 19 of 21 sections are stable.
- **System reminders counter attention decay (§2.3.4, §3.2 lesson).** After 15–30+ tool calls agents reliably violate system-prompt instructions (premature completion, exploration spirals, abandoned error recovery). Eight event detectors inject short single-purpose reminders at maximum recency, as `role: user` (empirically higher compliance than `role: system`), capped per type (`MAX_TODO_NUDGES=2`, `MAX_NUDGE_ATTEMPTS=3`; one-shot signals fire once). 24-template catalog across six categories.
- **Extended ReAct loop: separate thinking phase (§2.2.6, §3.2 lesson).** A tool-free thinking LLM call produces reasoning without tool schemas present; it is the *absence of tool schemas*, not an instruction, that stops premature action. Four depth levels (OFF/LOW/MEDIUM/HIGH); self-critique auto-included only at HIGH (per-turn critique was too slow). Doom-loop detection fingerprints (MD5 of tool name+args) over a 20-call sliding window; ≥3 identical fingerprints triggers a warning, then an approval pause — catches stuck loops within 3 repetitions where iteration caps were too coarse.
- **Design for approximate outputs — 9-pass fuzzy edit (§2.4.2, §3.4 lesson).** `edit_file` uses a chain-of-responsibility of nine progressively relaxed matchers (exact → line-trimmed → whitespace → indentation → escape → context-anchor), each returning the actual substring found so formatting is preserved; short-circuits on exact match for zero overhead. A prior two-pass strategy was the single largest source of "content not found" errors.
- **Lazy tool discovery via MCP + calibration (§2.4.7, §3.1, §3.5 lessons).** Loading all MCP schemas at startup consumed **40% of context before the first message**; lazy keyword-scored discovery cut baseline to **under 5%**. Context is calibrated from the API's reported `prompt_tokens` (not local estimates), since providers inject invisible content (safety preambles, tool schemas) that caused compaction to fire too late. Empirical threshold tuning is preferred over first-principles calculation.

## Relevance to the book
"AI-dō" is a practical guide to working with AI whose own examples run on terminal coding agents like Claude Code, so this paper is directly load-bearing for expanding Chapter 4 §4.2.1 "Harness Engineering". It uniquely provides an open, component-level anatomy of a real terminal coding-agent harness — the exact scaffolding/harness split, the five-stage compaction pipeline, just-in-time system reminders, and schema-level safety — with concrete measured effects (~54% context reduction, ~88% cache savings, 40%→<5% MCP overhead) and candid design-evolution notes on what failed first. It gives the book a citeable, practitioner-grounded vocabulary for scaffolding, harness, and context engineering that generalizes across CLI agents rather than being tied to any one closed product.

## Stance
Supporting (practitioner blueprint) — an experience report, not an evaluation; strong on design rationale, explicitly lacks benchmark validation.
