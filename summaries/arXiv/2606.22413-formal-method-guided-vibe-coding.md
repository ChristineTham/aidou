# Formal-Method-Guided Vibe Coding: Closing the Verification Loop on AI-Generated Safety-Critical Software Through Model-Driven Engineering

> Source: arXiv:2606.22413 (2026-06-21). Wei, Zhu, Wang, Woodcock, Yan, Foster & Ji. PDF in `../../sources/arXiv/2606.22413-formal-method-guided-vibe-coding.pdf`.

## Thesis
Vibe coding (accepting LLM-generated source from natural-language intent with minimal review) is fast enough for low-criticality consumer software but offers no path to certification for safety-critical systems governed by DO-178C, IEC 61508, or ISO 26262, because LLMs give no formal correctness guarantees. Rather than force the LLM to write scarce verification-aware languages (Dafny, Verus, Lean) or bolt on a post-hoc filter, the authors build Forge: a closed-loop pipeline that keeps the LLM generating ordinary Java, extracts formal models from that Java via Model-Driven Engineering, checks them with three complementary verifiers, and turns every verification failure into a structured correction prompt for the next generation pass. The LLM is the draft generator; the MDE-plus-verifier chain is the discriminator; the developer never reads the formal models.

## Key findings
- No cold, single-pass vibe-coding run converges to fully verified code: 0 of 30 cold runs (10 per case study) met the strict convergence criterion (all three verifiers pass plus a clean vacuity audit) (p. 13, Table 5).
- With the feedback loop, all 15 runs (5 per case study) converged to fully verified code, at a median of 2 iterations (range 2-3), and iteration count did not grow with case-study size (23 to 81 requirements) (pp. 14-15, Table 6).
- The verifier feedback specifically drives convergence, not iteration alone: a compile-only ablation that hides only the verifier output left all 15 runs producing verification-failing artefacts (15/15) (p. 16, Table 7).
- The three verifiers are complementary, not interchangeable: Dafny was the sole verifier catching a defect at 6 stop points and Isabelle at 2; each catches a distinct defect class (contract violation, behavioural vs structural deadlock, divergence, invariant violation) that the others miss (pp. 12-13, 16, Tables 4 & 7).
- The active LLM was Anthropic Claude Opus 4.8, driven through Claude Code; a converging run cost roughly 250,000-500,000 output tokens and 1-15 minutes of pipeline wall-clock, dominated by the Isabelle proof (pp. 11, 15).
- The pipeline is generic: switching between the three externally-authored case studies required editing one line of a manifest, with no changes to transformation source, runner code, or feedback parsers (RQ1, p. 11).

## Relevance to the book
This is the peer-reviewed, quantitative counterweight Chapter 3 needs to the Ahuja opinion pieces on vibe coding vs spec-driven development. It concedes vibe coding's speed benefit yet shows empirically, with controls and ablations, that unguided intent-to-code produces no assurance-grade evidence and never converges on a verified result alone; correctness comes from an external discriminator loop, not from the model. The "LLM as draft generator, verification infrastructure as discriminator" framing, and its explicit parallel to how safety-critical software has always been built (engineer authors the spec, tools verify the implementation), is a concrete bridge between the vibe-coding and spec-driven camps and directly informs the intent-driven-development (ICE) discussion. It also happens to run on the same Claude Opus 4.8 the book uses.

## Stance
empirical-vibe (also vibe-critical): an empirical study that treats vibe coding as a real, adopted paradigm but demonstrates with controlled experiments that it needs an external formal-verification feedback loop to reach correctness for safety-critical work; frames the LLM as a draft generator rather than an oracle.
