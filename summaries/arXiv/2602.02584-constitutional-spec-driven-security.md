# Constitutional Spec-Driven Development: Enforcing Security by Construction in AI-Assisted Code Generation

> Source: arXiv:2602.02584 (2026-01-31). Srinivas Rao Marri. PDF in `../../sources/arXiv/2602.02584-constitutional-spec-driven-security.pdf`.

## Thesis
AI-assisted "vibe coding" accelerates development but produces code that optimizes for functional correctness over security, so vulnerabilities are introduced systematically. The paper proposes Constitutional Spec-Driven Development (CSDD): a versioned, machine-readable "constitution" that encodes non-negotiable security constraints (mapped to CWE/MITRE Top 25) at the specification layer, so AI-generated code is secure by construction rather than by post-hoc inspection. The author argues the perceived choice between AI velocity and security is a false dichotomy, resolvable by constraining generation before code is produced rather than reviewing it afterward.

## Key findings
- In a banking-microservices case study, constitutional constraints reduced detected CWE violations by 73% (3 vs 11), cut time-to-first-secure-build 56% (4 vs 9 days), and cut security-review iterations 75% (1 vs 4) versus an unconstrained "vibe coding" baseline using the same AI (Claude) and developer (Table 3, p. 12).
- Constitution creation cost 16 hours upfront but was recovered through a 4x reduction in security-review cycles; compliance documentation coverage rose to 100% vs 23% (4.3x) (Lesson 8, p. 14; Table 3).
- Context-window management mattered: feeding the full 15-principle constitution gave 78% compliance ("inconsistent"), while selecting only 3–5 task-relevant principles gave 96% ("high"); a hierarchical 5–8 strategy gave 91% (Table 5, p. 14).
- Iterative regeneration with explicit principle references converged faster than manual patching (1.4 vs 3.2 iterations); automated traceability tooling hit 100% accuracy vs 94% manual (Lessons 6–7, p. 14).
- The author cites prior evidence that AI code is often insecure: Pearce et al. found Copilot produced vulnerable code in ~40% of security-relevant scenarios; Perry et al. found AI-assisted developers write less secure code; Liu et al. (2026) found 26.1% of 31,132 AI agent skills contained a vulnerability (pp. 3–4).
- Limitations are stated frankly: n=1 project (weak statistical power), single security-trained team (possible Hawthorne effect), coverage bounded to known CWE classes (no zero-days, no business-logic flaws), and the constitution file itself is a prompt-injection / "specification-poisoning" attack surface (pp. 15–16).

## Relevance to the book
This is peer-adjacent, empirically-grounded counterweight to Ahuja's opinion writing in Chapter 3: it takes vibe-coding seriously as a real and dominant practice, quantifies its security cost, and positions spec-driven development (via GitHub's Speckit / spec-kit) not as anti-AI ceremony but as the mechanism that makes AI velocity safe. It directly supports the chapter's SDD and intent-driven framing (constraints and intent living in specs above the code) while its explicit limitations section keeps the book honest about how thin the evidence base still is (single case study, self-reported metrics).

## Stance
pro-SDD — argues spec-driven development with embedded constitutional constraints outperforms unconstrained vibe coding; empirically flavoured (a comparative case study with numbers) but candid that it is a single-project study measuring documented traceability rather than proven security.
