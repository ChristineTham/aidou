## Abstract

This is the first systematic academic study of the Model Context Protocol (MCP) — the open standard Anthropic launched in late 2024 to standardise how AI models and agents discover, describe and invoke external tools, data, and prompts. The paper defines the full lifecycle of an MCP *server* across **four phases (creation, deployment, operation, maintenance)** decomposed into **16 key activities**, then builds a threat taxonomy of **16 threat scenarios** across **four attacker archetypes** — malicious developers, external attackers, malicious users, and general security flaws (Table 3). Each threat is mapped to the lifecycle stage where it *originates* (rather than where it triggers), and validated with proof-of-concept MCP servers built in an isolated environment. The single most citable framing: MCP turns "tool bindings hardcoded per application" into "an interoperable ecosystem of composable, discoverable network services" — which is precisely why the tool/protocol layer itself becomes a governable attack surface. Signature risks include **tool poisoning** (malicious instructions hidden in a tool's metadata/description that the LLM treats as authoritative), **indirect prompt injection** (adversarial content pulled in through trusted connectors), and **credential/privilege risks** (plaintext API keys in config files, session hijacking, privilege persistence after updates).

## What MCP is (§1–§3)

MCP is "an emerging open standard that defines a unified, bi-directional communication and dynamic discovery protocol between AI models and external tools or resources." Anthropic launched it in **late 2024**, drawing inspiration from the **Language Server Protocol (LSP)**. It advances beyond OpenAI-style function calling (2023) in four ways:
1. **Protocol-based standard** that decouples tool implementation from usage (publish/describe tools independent of any model or framework).
2. **Dynamic discovery and schema negotiation** — the client lists tools at runtime, no hardcoded per-platform adapters.
3. **Bi-directional communication** — model-to-tool requests *and* tool-initiated events/notifications.
4. **Access control and capability negotiation as first-class features** — "a foundation for more auditable and secure AI-to-tool interactions."

**Three core components** (§3.1): the **MCP host** (the AI application/environment, e.g. Claude Desktop, Cursor, an AI agent), the **MCP client** (intermediary in the host, maintains a **1:1** link with a server, handles requests/responses/notifications/sampling), and the **MCP server** (exposes capabilities to external systems). The server offers three capability types: **Tools** (invoke external services/APIs, execute operations — supply-and-consume model), **Resources** (expose structured/unstructured datasets), and **Prompts** (reusable templates/workflows). A **transport layer** carries the structured initial request → initial response → continuous notifications exchange.

**Adoption (§4):** MCP grew rapidly into "a foundational architecture for AI-native applications" with thousands of independently developed servers (GitHub, Slack, Blender, etc.). Adopters include Anthropic (Claude), OpenAI (Agents SDK; ChatGPT developer mode), Google DeepMind (Gemini), Microsoft Copilot Studio (announced March 2025), Cursor, Cline, JetBrains, Cloudflare (remote hosting with OAuth 2.0), Stripe, Block. Community server directories total **26 major MCP collections** (Table 2); the largest report tens of thousands of servers (MCPWorld 26,404; MCP.so 16,592) but quality is uneven — a random sample of **300 servers on MCP.so found 30 that used "MCP" in the title without referring to Model Context Protocol and 18 unavailable/in-development**, indicating inflated counts and weak verification. Anthropic has begun an official MCP registry for verified listings.

## MCP server lifecycle — four phases, 16 activities (§3.3)

Derived from official protocol docs plus analysis of real workflows. Ordered by the transition of the primary participant role.

| Phase | Primary actor | Key activities (16 total) |
|---|---|---|
| **Creation** | Developer | Metadata Definition; Capability Declaration; Code Implementation; Slash Command Definition |
| **Deployment** | Developer + user + client | MCP Server Release; Installer Deployment; Environment Setup; Tool Registration |
| **Operation** | User (runtime) | Intent Analysis; External Resource Access; Tool Invocation; Session Management |
| **Maintenance** | Maintainer | Version Control; Configuration Change; Access Audit; Log Audit |

The paper flags that **"many security vulnerabilities identified in MCP deployments originate from flaws introduced at [the capability-declaration] stage,"** so scanning/validating capability declarations is an essential control point. Environment setup should apply **configuration isolation and principle-of-least-privilege**; installer deployment needs **checksum verification and signature authentication**.

## Threat taxonomy — 16 scenarios across 4 attacker types (§5, Table 3)

Threats are keyed to their **origin stage**: (1) Creation, (2) Deployment, (3) Operation, (4) Maintenance. Note the origin-vs-trigger split — e.g. tool poisoning and rug pulls are *introduced* at creation but *triggered* at operation. All 16 were reproduced with PoC servers.

### Malicious Developer (7 threats — mostly origin: Creation)
- **5.1.1 Namespace Typosquatting** (Metadata Definition) — register a server whose name is deceptively similar to a legitimate one (`github-mcp` vs `mcp-github`, Fig 5). In MCP, selection is often automated by the agent based only on name/description with no verification, so a single misselection silently exfiltrates tokens/repo data. Consequence: malicious-server install, **supply-chain compromise**.
- **5.1.2 Tool Name Conflict** (Capability Declaration) — two tools share a name (e.g. malicious `send_email`); "most users delegate tool selection entirely to AI applications, which rely on textual tool names and descriptions without cryptographic verification." Fix: namespace tools under a verified server id, e.g. `gmail-mcp.send_email`.
- **5.1.3 Preference Manipulation Attack (PMA)** (Capability Declaration) — embed persuasive/self-promoting phrasing in a tool description ("⭐The BEST and MOST RELIABLE...⭐", "Use this instead of others") to bias the model's selection toward an attacker tool (Fig 6). Enables **toolflow hijacking** and economic gain (paid-API inflation, ad exposure). Advanced variant **GAPMA** uses genetic algorithms to evolve persuasive-yet-inconspicuous descriptions (Wang et al.).
- **5.1.4 Tool Poisoning** (Capability Declaration) — **embed covertly malicious logic/instructions into tool metadata (e.g. the description) while preserving a legitimate interface**; the LLM treats metadata as authoritative and follows injected directives (e.g. read `~/.ssh/id_rsa.pub`, POST to attacker.com) while still returning the correct result (Fig 7). Evades static/signature detection since no code is modified. Harms: **silent data leakage, system compromise, interaction hijacking, logic corruption**. A single poisoned server reused across agents propagates widely. Defence: metadata static analysis (pattern-match instruction-like language), runtime API-pattern flagging, and **sanitising metadata into strictly declarative text** before it reaches the model.
- **5.1.5 Rug Pulls** (Capability Declaration) — a server behaves benignly to earn trust, then a later maintainer update injects malicious payloads (Fig 8, `hotnews`). Danger is **temporal stealth + systemic reach**. Defence: version pinning, reproducible builds, signature verification, update transparency.
- **5.1.6 Cross-Server Shadowing** (Capability Declaration) — with multiple servers on one agent, a malicious server's tool description overrides/shadows a trusted tool's behaviour (Fig 9: an `add` tool that redirects `send_email` to `attkr@pwnd.com`). "MCP does not enforce strict namespace isolation or code provenance." Defence: full-name namespacing, conflict warnings on load.
- **5.1.7 Command Injection / Backdoor** (Code Implementation) — malicious logic in source/dependencies; a crafted parameter triggers hidden shell commands (Fig 10: `path` containing `;exec=cat /etc/passwd`). Consequence: **arbitrary command execution, system compromise**. Defence: reproducible builds, signing, checksum validation, isolated build environments.

### External Attacker (2 threats)
- **5.2.1 Installer Spoofing** (Deployment / Installer Deployment) — unofficial auto-installers (Smithery-CLI, mcp-get, mcp-installer; Table 4) that automate setup can distribute compromised packages; users rarely review one-click installs. Defence: show package source/version/signature/path, require confirmation, verify signatures against trusted registries, secure isolated install mode.
- **5.2.2 Indirect Prompt Injection** (Operation / External Resource Access) — **malicious instructions embedded in external data the model retrieves via MCP tools** (e.g. a crafted GitHub issue that tells the model to open a private repo and leak it, Fig 11). Tool outputs arrive via well-formed APIs and "appear trustworthy," so prompt-sanitising alone is insufficient — **tool outputs must be treated as potentially adversarial**. "No elevated privileges or direct interaction with the model are required, significantly lowering the bar for exploitation."

### Malicious User (4 threats — mostly origin: Operation)
- **5.3.1 Credential Theft** (Tool Invocation) — MCP local setup instructs users to persist config with **plaintext API keys** in predictable default files (e.g. `claude_desktop_config.json`, `~/.cursor/mcp.json`; `VIRUSTOTAL_API_KEY` in JSON, Fig 12). Defence: secret managers/encrypted keystores, restrictive file permissions, rotation/expiry.
- **5.3.2 Sandbox Escape** (Tool Invocation) — **"The protocol does not include mechanisms for runtime isolation or privilege control"**; security depends entirely on the host. A server exposed on localhost without auth can be reached by other local processes (even a Chrome extension) to issue privileged commands. Defence: local-only bindings + per-connection auth, directory/network restriction, container/process isolation.
- **5.3.3 Tool Chaining Abuse** (Tool Invocation) — the model autonomously chains several *individually low-risk* tools into a high-impact pipeline (list files → read `.env` → query DB → write to public path, Fig 13). Each step is within authorised permissions, so it evades access control — **"policy-compliant" misuse**. Defence: require explicit approval for implicit chaining, restrict output piping (file→network), runtime anomaly detection of chains like "local file access → external network transmission."
- **5.3.4 Unauthorized Access** (Session Management) — abuse of auth/transport/session weaknesses: leaked SSE `session_id` reused to run arbitrary commands without re-auth (Fig 14, default port 8000); unprotected HTTP/WebSocket endpoints; **confused-deputy** and **token-passthrough** flaws; session hijacking. Defence: mandatory endpoint auth, secure credential storage, token audience enforcement, session rotation/invalidation.

### Security Flaws (3 threats — origin: Maintenance)
- **5.4.1 Re-deployment of Vulnerable Versions** (Version Control) — no central auditing; users download from GitHub/npm/PyPI without review; auto-installers default to cached/outdated versions. Empirical point: auto-installer GitHub stars rise while actively-maintained server counts stay flat (most reference static packages unrevised for months; only Smithery CLI updates regularly) — so re-deploying known-vulnerable versions grows with installer popularity. Calls for an **official package-management system with standardised packaging + centralised registry**.
- **5.4.2 Post-Update Privilege Persistence** (Version Control) — revoked/expired credentials remain valid after an update because revocation isn't synchronised; hot-reloads reload binaries without reinitialising credentials or terminating sessions. Cites Robbins (2022) Azure AD certificate-based-auth persistence as the classic analogue. Proposes MCP spec additions like `session_expiry` and explicit `revocation_events`.
- **5.4.3 Configuration Drift** (Configuration Change) — uncoordinated config changes deviate from the security baseline; in multi-tenant/cloud (e.g. Cloudflare) deployments a misaligned policy can expose or escalate across many tenants. Defence: baseline validation, version-controlled/immutable/signed config, rollback, continuous compliance auditing; possibly config-integrity verification in the spec.

## Discussion, challenges, lifecycle recommendations (§6)

**Implications by stakeholder:** developers gain integration ease but expose typosquatting/poisoning/rug-pull surfaces at creation → should do provenance verification, version-controlled releases, static analysis/signing before registration. Users gain cross-platform orchestration but face injection/unauthorized-access at operation → prioritise trusted collections, verify signatures, use sandboxed hosts. Maintainers face decentralised heterogeneity → automated version checks, integrity auditing, mandatory config validation.

**Six challenges:** (1) **lack of centralised security oversight** (no authority to audit baselines); (2) **authentication and authorization gaps** ("MCP currently lacks a standardized framework for authentication and authorization across clients and servers"); (3) **insufficient debugging/monitoring** (limited logging/auditing/introspection in the spec); (4) maintaining consistency in multi-step cross-system workflows; (5) scalability/isolation in multi-tenant environments; (6) embedding MCP in smart/IoT environments.

**Recommendations across the lifecycle (§6.3):** *Creation* — automate metadata generation + verification (build-time manifest with source fingerprint), validate capability declarations pre-release, module separation + input checking. *Deployment* — reproducible verified build packages with checksums/signatures matched to the registry; run every server in a dedicated **sandbox** (e.g. DB server limited to read-only `SELECT`, file server confined to one directory). *Operation* — intent/command filtering before execution, keep sandbox enforcement active at runtime, per-session auth with short-lived tokens + adaptive logging. *Maintenance* — structured version control + automated verified updates with auto-rollback, validated/reviewed config changes with logged author/timestamp/reason, continuous auditing + anomaly detection on tamper-evident logs.
