# Spec-Driven Development: From Code to Contract in the Age of AI Coding Assistants

> Source: arXiv:2602.00180 (2026-01-30). Piskala, D. B. PDF in `../../sources/arXiv/2602.00180-spec-driven-code-to-contract.pdf`.

## Thesis
As AI coding assistants make code cheap to generate, the bottleneck shifts from writing code to specifying intent, so specifications—not code—should become the primary, authoritative artifact. Spec-driven development (SDD) inverts the traditional workflow: the spec is the source of truth and code is generated or verified against it. The paper is a practitioner's guide, presenting three levels of specification rigor (spec-first, spec-anchored, spec-as-source) and a decision framework for matching rigor to context. It explicitly frames SDD as an evolution of TDD/BDD made newly relevant by AI, not a revolution.

## Key findings
- SDD counters "vibe coding": loose prompts force LLMs to make dozens of unstated, often-wrong assumptions; unambiguous executable specs remove that guesswork and improve reliability (pp. 1-2).
- Nascent empirical studies cited suggest human-refined specs improve LLM-generated code quality, with controlled studies showing error reductions of up to 50% (p. 4, §IV).
- Three-level spectrum: spec-first (initial clarity, may drift), spec-anchored (living docs, tests enforce sync — the "sweet spot" for most production systems), spec-as-source (humans edit only specs, code regenerated — drift eliminated by construction) (pp. 2-3).
- Case study 1 (financial microservices, spec-anchored + OpenAPI/Specmatic): 75% reduction in integration/cycle time because incompatibilities were caught at spec review, not production (p. 5, §VI).
- Specs enable parallel multi-agent execution: work partitioned at the spec level lets multiple AI agents implement non-overlapping components simultaneously (p. 4).
- Named pitfalls: over-specification (spec becomes pseudo-code), specification rot/drift, spec-as-bureaucracy, tooling complexity, and "false confidence" — a passing spec test only proves code matches the spec, not that the spec is correct (p. 7, §IX).
- SDD is scoped, not universal: overkill for throwaway prototypes, solo short-lived projects, exploratory coding, and simple CRUD; the "golden rule" is minimum rigor that removes ambiguity (p. 7, §VIII).

## Relevance to the book
This peer-adjacent technical report directly complicates Ahuja's "SDD collapses" claim: it argues SDD is durable precisely because AI raises the value of clear specs, and it offers concrete evidence (75% integration-cycle reduction; up to 50% error reduction from human-refined specs). At the same time it is not naive cheerleading — it catalogs real failure modes (drift, over-specification, false confidence, bureaucracy) and bounds SDD's applicability, so it supplies balanced ammunition on both sides. It also usefully reframes the debate: SDD is positioned as the disciplined answer to vibe coding, and as "BDD with branding" (quoting Finster) rather than something new. This lets Chapter 3 present SDD as a spectrum of rigor rather than a binary that either works or collapses.

## Stance
pro-SDD (with quality-skeptic caveats) — advocates specs-as-source-of-truth and treats vibe coding as the problem SDD solves, but explicitly bounds SDD's value, names its pitfalls, and warns that passing spec tests do not guarantee correct software.
