# From Prompting to Verification: How Experience Shapes Vibe Coding Practices

> Source: arXiv:2605.24521 (2026-05-23). Fawzy, Tahir & Blincoe (Massey University & University of Auckland). PDF in `research/arXiv/2605.24521-experience-shapes-vibe-coding.pdf`.

## Thesis
A cross-experience survey of 162 vibe coders (non-developers, novices, professionals; 54 each) tests how "vibe coding" — generating software by natural-language prompting and judging outputs mainly by whether they run — varies with programming experience. The authors find that experience selectively shapes the practice: motivations, interaction styles, and quality-assurance (QA) behaviour differ across groups, but experiences and perceptions of code quality do not. They frame this as a *perception–action gap*: awareness of AI-code risks is broadly shared, but the capacity to evaluate, debug, and verify remains experience-dependent, making vibe coding only *partially* democratising.

## Key findings
- Awareness of code-quality problems is uniform, but verification is not. Across groups, perceived code quality (RQ3) showed no significant differences (p_BH = .884 for all themes, ε² ≤ .008) and experiences (RQ2) likewise showed none (p_BH ≥ .437, ε² ≤ .020); all groups agree AI code is "fast but flawed" and "prototype-ready only" (p. 20–21).
- Checking frequency rises with experience: ~45% of professionals report *always* checking AI-generated code before use, novices cluster in "often" (~45%), and non-developers were the *only* group reporting they *never* check code before use (χ²(8)=16.04, p=.042; p. 22).
- QA divergence is real but small-effect: non-developers reprompt instead of debugging more than professionals (p_BH=.037, ε²=.045) and hit "QA breakdown / confusion" more than both novices and pros (p_BH=.012, ε²=.068) (Table 7, Table 12, p. 18, 22).
- Regression: once usage variables (weekly vibe hours, adoption duration, independent non-vibe coding hours) are controlled, experience-*group* no longer predicts QA behaviour; the usage dimensions themselves do — more independent coding predicts less reprompting and more frequent checking (Table 11, p. 23). Skill comes from accumulated practice, not category label.
- Structured planning and verification-oriented prompting did NOT differ across groups (p_BH ≥ .177, ε² ≤ .012) and sat only at moderate agreement (Mdn≈4) for everyone — i.e., spec/plan-first discipline is weak across all experience levels (Table 6, p. 18).
- Interaction style shifts with experience: non-developers rely most on AI-led generation (delegating fully), professionals engage more in iterative dialogue (p_adj=.001) and rich context provision (p. 16–17). Context: only 33% of developers trust AI-code accuracy yet reliance keeps growing (p. 2, citing Stack Overflow 2025); ~a quarter of recent Y Combinator startups have codebases written almost entirely by AI (p. 2).

## Relevance to the book
This is the peer-reviewed empirical counterweight Chapter 3 needs against opinion-writer framing of the vibe-coding vs SDD debate. It supplies hard numbers showing vibe coding genuinely lowers the barrier to *producing* software but does not distribute the expertise to *evaluate* it — directly informing the ICE/intent-driven and spec-driven arguments. Crucially, its finding that structured planning and verification-oriented prompting are uniformly weak (not experience-driven) is evidence that discipline must be engineered into tooling/process, not assumed from seniority — a point that bridges to AI-native software engineering.

## Stance
empirical-vibe — a neutral, quantitative field study of vibe coding as practised, not an advocacy piece. It is descriptive rather than pro or anti, but its "perception–action gap" and verification-lag findings lend empirical support to the case for structured/spec-driven discipline over pure trial-and-error prompting.
